## 아이디어 조사 데스크 (2026-10-25, 개발완료)

무인 공장과 별개로, 사용자가 직접 굴리는 반자동 경로다. 모델을 부르지 않는다.

1. 콘솔 `#/ideas`에 아이디어 텍스트를 붙여넣는다 → 아이디어 ID(`I-yymmdd-xxxx`)와 전체 프롬프트(범용 메타 프롬프트 + 원문)가 생긴다.
2. 사용자가 전체 프롬프트를 복사해 자료봉(사용자의 별도 자료조사 에이전트: 웹·GitHub 가능, 이 PC 불가, 세션 간 대화 불가)에 준다 → 자기완결 하위 프롬프트 S1…Sn(3~6개)이 돌아온다.
3. 사용자가 각 하위 프롬프트를 새 세션에 붙여 병렬로 돌린다. 각 답은 `=== 자료봉 결과 ===`(아이디어 ID·하위과제 ID 포함) … `=== 끝 ===` 블록 하나다.
4. 결과를 같은 아이디어 화면(`#/idea/<ID>`)에 붙여넣는다(여러 블록 한꺼번에 가능, 다른 아이디어 ID면 거부, 형식 밖 텍스트는 `?`로 보관).
5. 관제용 저장: 콘솔 데이터 폴더 `ideas/ideas.sqlite`(붙여넣은 원문·파싱 결과)와 `ideas/briefs/<ID>.md`(원문 + 하위과제별 최신 결과 정리본 + 붙여넣은 원문 전부). 관제는 `docs/overseer-role.md`의 경로에서 읽는다.

- 코드: `src/all_tomorrow/console/ideas.py`, `src/all_tomorrow/static/console/pages/ideas.js`, 시험 `tests/test_console_ideas.py`.
- 설계 근거: 자료봉 조사 보고서 `docs/research/idea-pipeline-research-2026-10-25.md`. 메타 프롬프트는 아이디어 분석 → 핵심 불확실성 → 조사 과제(기본 3~5개, 독립/의존/교차검증/현장검증 분류) 순으로 분해시키고, 하위 프롬프트마다 `idea_brief·task_id·objective·scope·exclusions·source_policy·deliverables·completion_rule`을 넣게 한다. 결과 블록은 `상태: 완료|불완전|실패`와 주장별 근거(`- [C1] 주장` + `출처`·`인용`·`구분: 확인|추정`)를 담고, 붙여넣을 때 상태·주장을 파싱해 DB(`results.status`, `results.claims` JSON)와 화면·정리본 표(주장 수·출처 없음·추정)에 남긴다.
- 자료봉의 과제 쪼개기 답(분석·불확실성·과제 표)은 화면 `2-1` 칸에 붙여넣어 저장한다(`ideas.plan`, 다시 저장하면 바뀜). 정리본에 원문 다음으로 들어간다.
- 삭제: 아이디어 삭제(결과·붙여넣기·정리 파일까지)와 결과 하나 삭제(그 붙여넣기에 남은 결과가 없으면 붙여넣은 원문도)를 화면 버튼과 확인창으로 한다.
- 메타 프롬프트를 바꾸려면 `ideas/prompt.md`를 두면 내장본 대신 쓴다(`{idea_id}`·`{title}`·`{text}` 치환).

## 1. 완료된 상태

사용자가 웹에서 주제 하나를 던지면 다음이 무인으로 일어난다.

1. **아이디어 생성 담당**이 주제에 맞는 아이디어 후보를 낸다.
2. **신서사이저**가 특허·기존 서비스를 조사한다. 관련 특허나 이미 존재하는 서비스가 하나라도 있으면 근거 링크와 함께 퇴출한다(`이미 존재 → 폐기`).
3. 살아남은 아이디어는 **비저너리·오퍼레이터·애드보킷·스켑틱** 네 명의 회의에 올라간다.
4. 회의 결론이 "실제로 할 만하다"이면 **기획안**(문제·접근·DoD·리스크·시장/존재·관련 특허·공수)으로 사용자에게 보고된다.
5. 사용자는 기획안을 승인/거부하고, 그 판정이 직원 평가에 반영돼 승진·퇴출로 이어진다.
6. 이 모든 과정은 통제 콘솔에서 보이고 멈출 수 있다(RUN / 일시정지 / 재개 / KILL).

### 필수 조건과 선택 개선

| 필수 | 선택 (나중) |
|---|---|
| 주제 → 후보 → 특허/존재 필터 → 4인 회의 → 기획안 보고까지 한 번 끝까지 동작 | 다양성 모드, 자동 주제 발굴 |
| 퇴출마다 근거(특허번호/서비스 URL)가 남음 | 관련 특허 유사도 시각화 |
| 기획안 승인/거부 → 직원 점수 반영 | 자동 승진 정책 튜닝 |
| 키 풀에서 무료 키를 돌려 쓰고, 한도 초과 키는 자동으로 쉬게 함 | 키별 품질 측정 |
| 콘솔의 일시정지/KILL이 실제로 루프를 멈춤 | 서버·봇·투자 등 다른 메뉴 |

## 2. 파이프라인

```
주제(사용자) ─▶ 생성 담당 ─▶ 후보 N개
                              │
                              ▼
                       신서사이저 (특허·존재 조사)
                       │ 하나라도 걸림 → 폐기 + 근거 기록
                       ▼ 통과
              회의: 비저너리 · 오퍼레이터 · 애드보킷 · 스켑틱
                       │ 최대 R라운드, 각자 지지/반대 선언
                       ▼ 판정 = 할 만함
                   기획안 작성 ─▶ 사용자 보고 (대기 / 승인 / 거부)
                                         │
                                         ▼
                                  직원 평가 반영
```

### 단계별 정의

| 단계 | 입력 | 출력 | 실패/종료 |
|---|---|---|---|
| 생성 | 주제, 이전 폐기 목록 | 아이디어 후보 N개(제목, 한 줄 문제, 접근) | 후보 0개면 주제 재해석 1회 후 종료 |
| 신서사이저 | 후보 1개 | `통과` 또는 `폐기 + 근거[]` | 조사 소스가 모두 실패하면 통과시키지 않고 `조사 불가`로 보류 |
| 회의 | 통과 후보 + 조사 결과 | 4인 발언 기록, 최종 판정 | R라운드 안에 결론이 안 나면 `보류` |
| 기획안 | 판정 = 할 만함 | 기획안 카드 | — |
| 사용자 판정 | 기획안 | 승인/거부(+사유 선택) | 미응답은 `대기` 유지 |

**신서사이저의 "관련 특허"가 무엇인지가 이 시스템의 핵심 불확실성이다.** 기준이 느슨하면 거의 모든 아이디어가 폐기되고, 엄격하면 필터가 무의미해진다. 그래서 다음을 따른다.

- 판정은 "관련 있다"는 느낌이 아니라 **핵심 청구 요소가 겹치는지**로 내리고, 겹치는 요소를 근거에 적는다.
- 처음 2주는 폐기 판정 표본을 사용자가 검토해서(맞음/과잉 폐기) 기준을 조정한다. 이 검토 결과가 신서사이저 평가의 정답이 된다.
- 조사 소스 후보: KIPRIS Plus(국내 특허), Google Patents, 일반 웹 검색(기존 서비스 존재). 실제 사용 가능 여부와 무료 한도는 착수 시 먼저 확인한다.

### 회의 규칙

| 직원 | 역할 |
|---|---|
| 비저너리 | 크게 보면 무엇이 될 수 있는가, 확장성 |
| 오퍼레이터 | 만들고 운영하는 데 필요한 인력·비용·기간, 운영 난이도, 공수. 역할 지시문은 일반 기준만 담고, 의뢰인(실행할 사람)의 목표·일정 부하·고정 지출은 §3-1 권한으로만 받는다 |
| 애드보킷 | 사용자/고객 입장에서 왜 쓰는가, 지불 의사 |
| 스켑틱 | 왜 실패하는가, 숨은 전제와 리스크 |

- 각 라운드마다 네 명이 모두 `지지 / 반대 / 조건부` 선언과 근거를 남긴다.
- 통과 조건: 최종 라운드에서 4명 중 3명 이상 `support`. **최종 라운드에는 `conditional`이 없다**(구현 중 변경: 첫 실제 실행에서 4명 모두 두 라운드 내내 `conditional`만 내 회의가 결론을 못 냈다). 최종 라운드의 무응답·조건부는 반대로 센다.
- 초안의 "스켑틱 반대에 반박했는지" 조건은 자동 판정 근거가 약해 넣지 않았다. 운영 데이터로 다시 본다.
- 같은 모델이 네 명을 모두 연기하면 의견이 수렴하므로, 직원마다 다른 모델·프로바이더를 배정한다(화면의 gemini-free-lite / groq / gemini-free처럼).

## 3. 직원 제도 (승진·퇴출)

직원 = 이름 + 역할 프롬프트 + 배정된 모델 슬롯. 직원 자체가 아니라 **"이 역할을 이 모델로"** 라는 조합을 평가한다.

| 직원 | 평가 지표 (정답 출처) |
|---|---|
| 생성 담당 | 자기 아이디어가 최종 승인된 비율 |
| 신서사이저 | 폐기 표본 검토에서 맞은 비율, 놓친 기존 특허 수 |
| 회의 4인 | 자신이 지지한 기획안이 사용자 승인된 비율 / 반대한 것이 거부된 비율 |
| 공통 | 호출당 실패율, 응답 지연, 형식 위반 |

- **승진**: 더 좋은 모델 슬롯, 더 많은 호출 할당.
- **퇴출**: 일정 표본 이상에서 하위 지표가 계속되면 그 조합을 은퇴시키고 다른 모델로 신규 채용.
- 표본이 적을 때 판정하지 않는다(최소 표본 수를 정해 두고, 그 전엔 `평가중`).
- 모든 승진·퇴출은 근거 지표와 함께 감사 로그에 남는다.

## 3-1. 의뢰인 정보 접근 권한 (2026-10-19)

### 왜

- 처음에는 오퍼레이터 지시문에 사용자 자신의 운영 상황을 하드코딩했다. 외부 프로바이더로 나가는 유출이자 공장 제약이 평가에 섞이는 편향이라 `bb08077`에서 제거했다(아래 [관찰](#관찰-판단-필요)).
- 제거 후의 일반 지시문만으로는 "이 사람이 실행할 만한가"를 잴 척도가 없다. 그래서 의뢰인 사실을 Notion에서 읽고, **직원별로 등급·범위를 나눠** 필요한 만큼만 준다.
- 사용자 결정 (2026-10-19): 자신의 정보가 외부 무료 모델 프로바이더로 전송되는 것(학습 활용 포함)을 허용한다. 아래 제외 범위는 사용자가 아니라 구현 측이 정한 것이다.

### 모델

- 출처(`profile_sources`)마다 `level`(1~3)과 `scope`(goals / capacity / budget / interests).
- 직원(`staff`)마다 `access_level`과 `access_scopes`.
- 직원이 출처를 보는 조건: `source.level <= access_level` **이고** `source.scope ∈ access_scopes`. 받은 내용은 프롬프트 끝의 `[의뢰인 정보 — 네 권한 범위에서만 제공됨 …]` 블록으로 붙는다(`profile.context_block`). 볼 것이 없으면 블록 자체가 없다.
- 출처 하나는 최대 1,500자. 읽기 실패한 출처는 빈 값으로 처리하고 실행은 계속한다(오류 이름만 감사 로그에).

| 출처 | level | scope | 들어가는 것 (값이 아니라 구조) |
|---|:-:|---|---|
| 진행 중인 목표·프로젝트 | 1 | goals | 목표 DB의 `목표/프로젝트·상태·영역·기한`. 영역 개발/창작/입시/기타, 상태 탐색/진행/주력만 |
| 일정 부하 | 1 | capacity | 할 일 DB에서 **개수만**: 진행 중(완료·취소·보류 제외) 수, 그중 14일 안 마감 수. 할 일 내용은 안 보냄 |
| 다가오는 마감 | 3 | capacity | 할 일 DB에서 30일 안 마감인 진행 중 할 일의 `마감·영역·할일`. 영역 학교/숙제·공부·개발·입시·창작만 |
| 고정 지출·구독·수입 | 2 | budget | 지출 DB의 `항목·구분·금액·주기`, `활성` 체크된 행만. 첫 줄에 월 합계(수입 / 구독·고정·변동 지출 / 차액) |
| 취향·선호 | 3 | interests | 캐릭터 시트 페이지의 `선호`·`불호` 섹션 본문만 |
| 소비·사용 취향 | 3 | interests | 취향 페이지의 `예술·인물 취향`·`소비·착용`·`물건·기기 사용` 섹션 본문만 |

| 직원 | level | scopes | 따라서 보는 출처 |
|---|:-:|---|---|
| 아이디에이터 | 3 | goals, interests | 목표·프로젝트, 취향·선호, 소비·사용 취향 |
| 신서사이저 | 0 | — | 없음 (특허 조사 프롬프트에는 블록을 붙이지 않음) |
| 비저너리 | 1 | goals | 목표·프로젝트 |
| 오퍼레이터 | 2 | capacity, budget, goals | 목표·프로젝트, 일정 부하, 고정 지출 (회의 발언과 기획안 작성 모두). 승진 시 다가오는 마감 추가 |
| 애드보킷 | 0 | — | 없음 (고객 관점이 의뢰인 사정에 끌리지 않게) |
| 스켑틱 | 2 | capacity, budget | 일정 부하, 고정 지출. 승진 시 다가오는 마감 추가 |

### 승진·퇴출과의 관계

- 실제 level = config 기본 level + 승진 보너스(최대 3). 승진하면 보너스 +1. 감사 로그 `staff_promote`에 새 level이 남는다.
- config가 기본 level과 scopes의 원본이다. 기동할 때마다 config 값으로 다시 계산하므로, config에서 기본 level이나 scope를 내리면 다음 기동부터 권한이 실제로 줄어든다(승진 보너스는 유지).
- 퇴출 후 신규 채용은 보너스 0, 그 역할의 config 기본값으로 시작한다.
- 승진이 실제로 의미 있게: level 3 출처 `다가오는 마감`(capacity)을 두어, 오퍼레이터·스켑틱이 승진하면 일정을 더 자세히 본다. 비저너리(goals만)·신서사이저·애드보킷은 승진해도 새로 보는 출처가 없다.
- 설정 검증: 출처 level 1~3, 직원 level 0~3, scopes는 문자열 목록이어야 하며(문자열 하나면 부분 문자열 매칭이 돼 권한이 넓어짐) 어기면 기동 단계에서 실패한다.

### 회의 기록 전달 규칙

- 회의 발언에는 말한 직원이 본 의뢰인 정보가 섞일 수 있다(모델에게 "그대로 옮기지 말라"고 하지만 강제되지 않는다).
- 그래서 각 발언에 말한 직원이 본 출처 목록을 붙이고, 듣는 직원이 그 출처를 **모두** 볼 수 있을 때만 근거 원문을 전달한다.
- 그렇지 않은 직원에게 무엇을 주는지는 `council_share`로 정한다 (2026-10-19 사용자 결정: 중간안 `summary`).

| 모드 | 권한 밖 직원이 받는 것 |
|---|---|
| `summary` (기본) | 말한 직원이 같은 호출에서 함께 쓴 "의뢰인 사정상 ~" 수준 요약(`(요약)` 표시). 요약에 숫자가 있거나, 듣는 직원이 못 보는 출처에만 있는 단어가 있으면 버리고 `(권한 밖 근거 생략)` |
| `full` | 모든 근거 원문 (권한 분리는 처음 받는 의뢰인 정보에만 적용) |
| `filtered` | 입장만, 근거는 `(권한 밖 근거 생략)` |

- 이유: 다 공유한 실행에서 직원 넷이 같은 예산 수치로 반대해 5개 모두 0/4가 됐다. 애드보킷·비저너리는 의뢰인 사정과 떨어진 관점이 역할이라, 사정이 있다는 사실만 알고 수치에는 끌려가지 않게 한다.
- 출처 목록이 없는 발언(이 규칙 이전에 기록된 발언, 재개 시 복구된 run)은 볼 수 없는 것으로 취급한다(fail closed).
- 결과: 애드보킷은 다른 직원의 의뢰인 정보 기반 근거를 받지 않고, 비저너리는 목표만 본 발언만 받는다. 오퍼레이터는 스켑틱의 근거를 받는다(스켑틱이 본 출처 ⊆ 오퍼레이터).
- 사용자 본인 콘솔(로그인 필요)의 회의 기록·기획안에는 근거 전문이 그대로 보인다.

### 제외 (구현 측 결정)

- 일기, 건강·복약, 성·젠더, 자해, 인물·관계 기록은 출처로 **설정하지 않는다**. 어느 level로도 닿지 않는다(테스트가 해당 페이지/DB ID가 설정에 없는지 검사).
- 캐릭터 시트의 `기본 정보` 섹션은 건강 정보가 섞여 있어 제외한다.
- 2차 방어: `profile.SENSITIVE` 키워드에 걸리는 줄은 허용 섹션 안이라도 버린다. 설정 중 허용 섹션의 복약 관련 선호 한 줄이 처음 목록을 빠져나간 것을 확인해 목록을 넓혔다. 검토에서 띄어쓰기·대소문자·제로폭 문자·영어 표현이 빠져나가는 것이 확인되어, 매칭 전에 NFKC·소문자·문자/숫자만 남기는 정규화를 하고 영어·변형 표현을 추가했다. 키워드 목록은 완전할 수 없는 보조 장치이고, 1차 방어는 출처 자체를 설정하지 않는 것이다.
- Notion에는 아무것도 쓰지 않는다(조회만).

### 기록과 재현성

- 주제마다 한 번 `load_profile` DBOS step으로 스냅숏을 뜬다. 재개된 run은 같은 사실을 본다.
- 그 스냅숏(과 의뢰인 정보가 섞일 수 있는 회의 발언)은 DBOS 시스템 DB(이식본 기본 `.artifacts/console/factory/idea-factory-dbos.sqlite`, Git 제외)에 주제마다 남는다. 웹으로 노출되지는 않지만 이 PC의 파일 접근으로는 읽힌다. 중앙 서버로 옮길 때 DB 접근 범위를 다시 본다.
- 감사 로그 `profile_access`: 주제 ID, 직원별로 받은 **출처 이름**(내용 없음), 실패한 출처의 오류 이름. 이벤트 로그에는 직원별 받은 출처 수.
- 콘솔 직원 화면에 직원별 권한(`L{level} · scopes`) 열.
- 비밀값: `NOTION_TOKEN`은 `~/.all-tomorrow/key-pool.env`(저장소 밖), 이름만 `config/key-pool.example.env`. 현재 코드는 `NOTION_TOKEN`만 읽고, 출처 ID는 `config/idea-factory.yaml`에 있다. `NOTION_TOKEN`이 없으면 아무도 의뢰인 정보를 받지 않는다.

## 4. 무료 키 풀

- 기존 Stage 0 선택인 **LiteLLM 게이트웨이**의 router로 키를 묶는다. 새 LLM 클라이언트를 만들지 않는다.
- 키별 상태: `사용 가능 / 쿨다운(429) / 소진(일 한도) / 무효`. 429는 쿨다운, 401/403은 무효 처리.
- 직원 슬롯은 "특정 키"가 아니라 "모델 그룹"을 가리키고, 키 선택은 router가 한다.
- 키 값은 서버 환경/비밀 저장소에만 두고, 로그·이벤트·화면에는 키 ID(끝 4자리)만 남긴다(README의 credential 불변식).
- **계정 정책 (2026-10-19 사용자 결정)**: 같은 프로바이더의 여러 계정 키를 모두 풀에 넣는다. 모두 사용자 소유 계정이고, 약관 위반(아래 확인표)에 대한 책임은 사용자가 진다. 키는 재발급하지 않고 그대로 쓴다.
- 키 원본: `~/.all-tomorrow/key-pool.env`(저장소 밖). 이름 템플릿: `config/key-pool.example.env`. 점검: `scripts/check_key_pool.py`.
- **유료 키 보호**: OpenRouter `/api/v1/key`에서 `is_free_tier=false`인 키(DUCKPYO_LEE 계열, 특히 한도 없는 DDD)는 `:free` 모델에만 연결한다. 유료 모델 deployment에는 넣지 않는다.

## 5. 웹사이트 구조 개편

### 원칙

- **구조는 데코 콘솔을 따른다**: 왼쪽 섹션 메뉴 + 섹션 안 하위 화면 + 메뉴 검색.
- **디자인은 미니멀리즘을 유지한다**: 단색 배경, 강조색 하나, 그라데이션·이모지 아이콘·글로우 없음, 텍스트 우선, 카드 테두리는 1px 회색. 현재 사용량 패널 스타일을 기준으로 삼는다.
- **실제 데이터가 있는 화면만 만든다.** 데코 콘솔의 186개 화면을 빈 껍데기로 복제하지 않는다. 메뉴는 기능이 생길 때 하나씩 추가한다.

| 모니터링 | 구독 사용량, 키 풀 상태 | usage snapshot, LiteLLM | ✓ |
| 자율 레이어 | 통제면(루프 상태·RUN/일시정지/재개/KILL·직원 카드·이벤트 로그), 목표 지정 | 아이디어 공장 런타임 | ✓ |
| 기획안 | 전체/대기/승인/거부 탭, 주제별 묶음 | 기획안 저장소 | ✓ |

### 기술 방향

- FastAPI는 그대로 두고, 현재 문자열 HTML 한 장을 **정적 셸 하나 + 화면별 모듈**로 나눈다. 프레임워크 없이 hash 라우팅 + fetch. (빌드 단계를 늘리지 않기 위함. 화면이 많아져 유지가 어려워지면 그때 재검토)
- main에서는 이 구조가 `/`의 섹션 셸(`static/console`)로 들어갔다. 기능마다 `all_tomorrow.console.<feature>` 라우터(`build_router(ctx)`)와 `static/console/pages/<feature>.js`가 짝이다. 이전 대시보드는 `/requests`, 기기·계정 화면은 그대로다.
- 모바일 폭(데코 화면처럼 폰에서 확인)에서 메뉴는 접히는 서랍으로.
- 콘솔 갱신은 5초 폴링으로 시작한다. 실시간 스트림은 필요가 확인되면 추가.

## 6. 어디서 돌리나

- 아이디어 공장 루프와 키 풀: **중앙 서버** — tailnet의 `all-tomorrow-central` (Linux, `http://100.97.113.3:8080`). 무료 API만 쓰므로 이 PC 로그인에 의존하지 않고 24시간 동작할 수 있다. (이식 전 계획은 "AWS 서버"였다.)
- 확인된 충돌 (미결정): `deploy/docker-compose.yaml`의 단일 노드 구성에는 이미 LiteLLM proxy가 `127.0.0.1:4000`에 있고, 아이디어 공장 gateway의 기본 포트와 `IDEA_FACTORY_GATEWAY_URL` 기본값도 `127.0.0.1:4000`이다. 중앙 서버에 올릴 때 그 proxy에 deployment를 합칠지, 다른 포트로 따로 둘지 정해야 한다. 그 compose가 중앙 서버에 실제로 떠 있는지는 이 문서에서 확인하지 않았다.
- 루프의 durable 실행(중단 후 재개, KILL)은 Stage 0에서 선택한 **DBOS**를 쓴다. 자체 queue/lease를 만들지 않는다.
- 로컬 coding worker(Codex 등)는 이번 범위에서 쓰지 않는다. 승인된 기획안을 실제 구현으로 넘기는 연결은 다음 단계.

### 실행

```powershell
# 1) gateway (별도 창)
.venv/Scripts/python.exe -m all_tomorrow.idea_factory gateway --litellm .artifacts/gateway-venv/Scripts/litellm.exe
# 2-a) CLI로 주제 하나
```

### 구현 중 발견하고 고친 것

- 회의가 결론을 못 냄 → 최종 라운드 `conditional` 제거(§2 회의 규칙).
- KILL 버튼 500: DBOS 동기 API를 async 핸들러에서 호출 → 스레드에서 호출.
- KILL이 일부만 적용된 주제가 크래시 후 복구되면 `해제` 시 다시 돌던 문제 → checkpoint가 주제 상태도 확인, KILL은 취소 전에 주제를 KILLED로 기록(`test_killed_topic_stays_killed_after_loop_reset`).
- 승진 직후 같은 표본으로 또 승진하던 문제(초 단위 시각 비교) → 마이크로초 시각 + 엄격 비교.

### 관찰 (판단 필요)

- 회의 통과율이 낮다. 2번째 주제는 5개 모두 탈락(지지 1~2/4). 오퍼레이터·스켑틱이 "무료 키·1인 개발자" 제약으로 자주 반대했다.
- **정보 유출 수정 (2026-10-19)**: 그 제약은 오퍼레이터 역할 지시문에 사용자 자신의 운영 상황(1인 개발, 무료 API 키, AWS 프리티어)을 넣었기 때문이다. 이 지시문은 외부 무료 프로바이더로 전송되므로 사용자 정보 유출이고, 아이디어 평가에 공장 자체의 제약이 섞이는 편향이기도 했다. 역할 지시문을 일반적인 실행 가능성(인력·비용·기간·운영 난이도)으로 바꿨다. 모델로 보내는 모든 프롬프트에 이런 표현이 없는지 테스트로 검사한다. 이전 실행의 탈락률은 이 편향이 섞인 값이므로 기준 판단에 쓰지 않는다. 이후 의뢰인 사실은 직원별 권한으로만 전달한다(§3-1).
- 이미 외부로 나간 프롬프트(실행 6회 분량)는 회수할 수 없다.
- Gemma 무료 모델은 upstream 429가 잦아 비저너리 호출 상당수가 `g-fast`로 넘어간다(fallback). 직원별 모델 다양성이 그만큼 줄어든다.
