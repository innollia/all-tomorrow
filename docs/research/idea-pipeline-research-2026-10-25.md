# 사업 아이디어 병렬 자료조사 파이프라인 — 기술·설계 조사 보고서 (자료봉, 2026-10-25)

사용자가 자료조사 에이전트에게 받아 관제에 건넨 보고서 요약 원문. 이미지 링크는 생략.

## 1. 핵심 조사 결과

구상한 파이프라인은 Orchestrator–Workers 구조와 가깝지만, 사용자가 프롬프트를 직접 분배하고 결과를 수집한다. 그래서 실시간 통신보다 과제 분해, 독립 실행 계약, 결과 보존, 근거 추적이 중요하다.

- 발견 1 — 동적 과제 분해가 고정 카테고리보다 유연하다. STORM은 주제별 관점을 구성해 질문을 만들고, Anthropic도 독립 탐색 방향을 나눠 병렬 조사한다. 유형별 기준을 활용해 동적으로 과제를 만든다.
- 발견 2 — 병렬 에이전트 수 자체가 목표가 아니다. 멀티에이전트는 결과가 좋지만 토큰이 크게 늘고, 선후 의존이 강한 작업엔 불리하다.
- 발견 3 — 가장 위험한 단계는 결과를 믿고 합치는 단계. DeepTRACE(ICLR 2026): 인용 정확도 40~80%, 출처 없는 주장 다수. 보고서 단위 출처 목록이 아니라 개별 주장–근거를 연결해야 한다.

잠정 설계: 기존 웹사이트 유지, 조사 작업을 각각 독립 실행 가능하게, 원문 결과 보존.

## 2. R1 — 병렬 조사 과제 만들기

- STORM/Co-STORM: 관점 기반 질문 생성 → 아이디어마다 조사 분야를 동적으로 선택.
- Anthropic Research: 총괄이 목적·범위·출력 형식·탐색 지침을 지정. 모호하면 중복 조사·누락 발생 → 자료봉이 프롬프트뿐 아니라 작업 경계를 생성해야 한다.

3단계 분해:
1. 아이디어 분석 — 제품, 고객, 문제, 수익 방식, 현재 근거, 중요한 가정 추출. 미확정은 가정으로 표시.
2. 핵심 불확실성 식별 — 성공을 크게 바꿀 미검증 가정. 시장·기술·법률 분야는 분류 도구일 뿐 고정 목차 아님.
3. 독립 조사 과제 생성 — 단독 실행 가능? 다른 결과 대기 필요? 실제 의사결정에 쓰이나? 검사.

| 분류 | 예시 | 처리 |
|---|---|---|
| 독립 조사 | 경쟁사 조사와 법률 조사 | 병렬 |
| 의존 조사 | 기술비용 산출 후 가격모델 검증 | 순차 또는 가정을 명시한 병렬 |
| 교차 검증 | 주요 경쟁사 매출 추정 검증 | 독립적으로 중복 조사 |
| 현장 검증 | 실제 고객 구매 의향 | 조사로 가설 작성 후 직접 검증 |

기본 3~5개 과제(사용자 수동 작업 부담 고려, 검증된 최적값 아님).

## 3. R2 — 독립 조사 에이전트 프롬프트 계약

공유 기억이 없다는 전제로 각 프롬프트에 포함:

| 필드 | 목적 |
|---|---|
| idea_brief | 전체 아이디어 공통 맥락 |
| task_id | 작업–결과 연결 |
| objective | 답해야 할 핵심 질문 |
| scope | 반드시 다룰 범위 |
| exclusions | 다른 작업과 중복 방지 |
| source_policy | 허용 출처, 조사 시점, 검증 조건 |
| deliverables | 결과 형식·필수 산출물 |
| completion_rule | 완료·불완전·실패 구별 조건 |

(보고서는 여기서 끊겨 전달됨)
